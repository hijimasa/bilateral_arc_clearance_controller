## 対象と方法

Ackermann motion model 対応を対象とする。設計方針は「nav2 MPPI の `AckermannConstraints` と同じ粒度」、
すなわち車両モデルを最小旋回半径 `turn_radius_min` による**車体曲率**の制約のみで記述し、wheelbase・
実舵角・操舵速度は下位の車両controllerの責務とする、というものである。

3系統の独立レビューを並列に実施した。

1. **C++実装の正当性**: 数値的edge case、後退時の符号、`limitReachableCommand` の適用順序、
   `BacCore` の値意味論とdangling reference、出力段の反復ループ、差動二輪へのリグレッション。
   検証手段として HEAD 版と作業ツリー版の差分fuzz（24 000 tick）、Ackermann不変条件fuzz
   （72 000 tick）、ASan/UBSanを用いた。
2. **文書と実装の整合**: パラメータ表と `declareCoreParameters` の突き合わせ、挙動記述の真偽、
   日英版の食い違い、テスト記述と実物の一致。
3. **テスト品質のミューテーション検証**: 実装を意図的に壊し、テストが落ちるかを機械的に確認する。

## 結論

安全側の主要不変条件は成立している。Ackermann の `process()` 出力から、その場旋回も最小旋回半径違反も
1件も生成できなかった（72 000 tick）。`BacCore` の値意味論はASan/UBSanでcleanであり、
差動二輪の17シナリオ harness 出力は refactor 前後で byte-identical である。

一方で、**設定却下時の例外安全にHigh 1件**、**文書が実装と異なる廃案設計を記述している状態がMedium 1件**、
**テストの主要アサーションが空振りしている状態がMedium 1件**を確認した。特に後者は、レビュー対象の
テストが「実装を壊しても緑のまま」であることをミューテーションで実証したものであり、テスト件数の
増加が保護の増加を意味していなかった。

## High

### H1 — 却下された設定が半適用され、直進指令が全舵切りへ化ける

`BacCore::setParams` は `params_ = params;` を実行した**後**に `rebuildMotionModel()` を呼ぶ。
motion model は `const Params &` で `BacCore::params_` を参照するため、rebuild が throw した場合、
生き残った旧modelが**却下されたはずのパラメータ**を読む状態になる。objectは生存し、`params()` は
不正値を返し、`process()` はその設定のまま動き続ける。

`turn_radius_min` を符号typoで `1.0 → -1.0` にした再現結果:

```text
setParams threw: bac: Ackermann turn_radius_min must be positive
healthy Ackermann         limitReachableCommand((0.3,0),(0.3,0)) = (0.3000,  0.0000)
after rejected setParams  limitReachableCommand((0.3,0),(0.3,0)) = (0.3000, -0.3000)
```

`yawRateBound` が `min(w_max, |v| / -1.0)` すなわち**負の上限**を返し、
`std::min(std::max(w, -bound), bound)` は `bound < 0` のとき無条件に `-|bound|` へ潰れる。結果として
**直進指令が全舵切りの旋回として返る**。`turn_radius_min = 0` の場合はゼロ除算で `inf` となり、旋回半径
制約が無言で消える（こちらは失敗がより静かな分たちが悪い）。

同梱の2つのadapterからは到達しない（`declareCoreParameters` が `setParams` 到達前にthrowし、tick毎の
`setParams` は `limits.v_max` しか変えない）。したがって現場の不具合ではなくライブラリ契約の不具合だが、
公開ライブラリとして `setParams` の例外安全は満たすべきである。既存テストは `setParams` がthrowすること
だけを検査しており、**throw後にobjectが使用可能である**ことを検査していない。

## Medium

### M1 — 文書が実装されていない廃案設計を記述している

文書は `motion_model.wheelbase`、`motion_model.max_steering_angle`、`motion_model.max_steering_rate`
という**コードに存在しないパラメータ**を表に載せ、実舵角をsampleして `w = v tan(delta) / L` へ変換すると
記述していた。実装は車体曲率方式であり、これらのパラメータは宣言されていない。文書に従った利用者は、
何も効かない3つのパラメータを設定することになる。

作業ツリーで文書は書き換えられたが、書き換え後にも次の5件の誤りが残っていた。

1. `docs/algorithm.md` / `docs/en/algorithm.md`: 「差動二輪は曲率を制約しない」。実際は
   `DiffDriveMotionModel::isCommandKinematicallyValid` が並進候補を `|v|/|w| >= turn_radius_min` で
   弾く。制約が無いのは `v≈0` の旋回行のみ。同packageの `parameters.md` の記述とも矛盾する。
2. Ackermannのsample範囲を `|kappa| <= 1 / turn_radius_min` と記載。実際の
   `curvatureBound = min(1/turn_radius_min, w_max/|v|)` であり、`|v| > w_max * turn_radius_min` の
   速度域では `limits.w_max` が**候補曲率の格子自体**を狭める。また「各前進速度について」は不正確で、
   後退速度も同じ範囲で扱われる。
3. 後方goal試験の差動二輪参照を「同一条件」と記述。実際は `makeDiffDriveReference` が motion model と
   `turn_radius_min`（1.0 → 0.25）の2つを変えている。
4. `velocity_min` の説明がAckermannで不足。差動二輪は `v` のみ0にするが、Ackermannは指令全体を
   `{0,0}` にする。直下の `angvel_min` 行はモデル別に書き分けており、非対称である。
5. `turn_radius_min` の日本語版が「前進候補」。コードは `fabs(command.v)` を見るため後退も同じ
   ガードにかかる。英語版は "translating candidates" と正しく、日英で唯一の事実の食い違いだった。

なお、46個の宣言済みパラメータと既定値の突き合わせ、相互リンクとanchor、README掲載の走行時間4件の
再現性については誤りを確認しなかった。

### M2 — テストの主要アサーションが空振りしている

ミューテーション検証により、テストが実装の破壊を検出しないことを実証した。survivedは「実装を壊しても
テストが緑のまま」を意味する。

| ミューテーション | 結果 |
|---|---|
| `commandChange` を曲率差からヨーレート差へ | SURVIVED |
| `clearanceProbeCommands` を旋回半径無視の固定値へ | SURVIVED |
| `applyCommandDeadband` を差動二輪と同じ独立deadbandへ | SURVIVED |
| sampler が `linear_speed_cap` を無視 | SURVIVED |
| `isCommandKinematicallyValid` が常にtrue | SURVIVED |
| refinement が曲率上限のclippingを行わない | SURVIVED |
| 明示的な直進候補を曲がった候補へ差し替え | SURVIVED |
| `setParams` がmodel typeの切替を無視 | SURVIVED |
| `bac_core.cpp` の goal進捗ゲート除去 | SURVIVED |

特に重大なのは最後の1件である。`testRearGoal` の合格条件 `min_goal_distance > 2.5f` は
**「goalに近づかなかったこと」**しか要求しないため、goalから遠ざかる方向へ 3.998 m 走行しても合格する。
本来意図した「その場に留まる」は検査されていなかった。

空振りと判定したアサーションは次のとおり。

1. 「Ackermann hysteresis is measured in curvature」: 比較する2指令が同一速度を共有するため、曲率差と
   ヨーレート差は定数倍の関係にあり、大小関係はどちらの定義でも成立する。命名した性質を区別できない。
2. 「every sampled moving candidate is kinematically valid」: 述語とsamplerが同じ `yawRateBound` で
   定義されており `A(f(A))` の形。実際に効いているのは独立計算の半径比較の方である。
3. 「the wide vehicle stays within its 3 m turning circle」: 2行上の `!violated_turning_radius` と
   定義上同一の検査であり、独立に落ちることがない。
4. `ros_adapter_unit.cpp` のAckermann旋回半径検査: 当該tickの出力は厳密に `(0, 0)` であるため
   `if` に入らず、**到達不能なコード**である。テストに見えて何も検査していない。

一方、`testRearGoal` の差動二輪参照は end-to-end のその場旋回ミューテーションを閉ループで殺した唯一の
検査であり、意味のあるガードとして機能している。他の4シナリオの「その場旋回を使わない」は、goalが前方で
そもそも旋回が選ばれない配置のため空振りだった。

差動二輪側については `withLinearSpeed`、`commandChange`、`isInPlaceRotationAdmissible` の
ミューテーションがいずれもKILLEDであり、**refactorによるcoverageの喪失は確認しなかった**。

## Low

### L1 — 差動二輪の挙動が0.33%のtickで変化しており、`Status` が変わる

17シナリオ harness は byte-identical だが、パラメータをランダム化した開ループ差分fuzz（24 000 tick）で
79 tick（0.33%）の差異を確認した。うち71 tickは、旧実装が
`isInPlaceRotationAdmissible` の検査を**経ずに**出力していたその場旋回 `(0, w)` を、新実装が `(0, 0)` へ
置き換えたものである。新実装の方が正しい（旧実装は乱雑環境で旋回していた）。ただし観測可能な副作用が
2点ある。

- `avoid_status` が `AVOIDING`(1) から `STOP`(2) へ変わる。`bac_filter_node` はCLEARのみで分岐し、
  nav2 pluginはstatusを使わないため影響範囲は当該topicの購読者に限られる。
- 旋回不許可時に `out_w` を1 tickで0へ落とすため、`acc_w * control_period` の到達可能性契約を
  安全側に破る。

残る8 tickは意図した曲率保存型の減速であり、いずれもループ内で接触再検査を通っている。

### L2 — Ackermann sampler が自身のvalidatorが拒否する候補を生成しうる

`curvature()` と `yawRateBound()` は `1e-4`、`isCommandKinematicallyValid` は `1e-3` を停止判定に使い、
閾値が不整合である。`sampleCandidates` の後退escape行は `v_rev < -1e-3` を確認してから `v_rev` と
`v_rev / 2` を push するが、後者は再確認されない。`limits.v_min = -0.0015` で
`(-0.00075, ±0.0015)` 等が生成され、validatorはこれを不正と判定する。

`bac_core.cpp` 側では当該候補が `|v| <= 1e-3` の turn-then-go 分岐へ入りvalidatorを呼ばないため、
現状は潜在的である。成立には `|v_min| < 0.002` が必要で、現実的な設定では起こらない。

### L3 — `refinementCandidates` が `bound == 0` で重複候補を返す

`limits.w_max = 0` のとき `coarse_step = 0` となり、全offsetが0に潰れて `2 * w_refine_steps` 個の
同一指令を返す。NaNやcrashはなく無駄な評価のみで、差動二輪も同形である。`bac_controller.cpp` は
configure時に `w_max <= 0` を拒否するが、`bac_filter_node` は拒否しない。

### L4 — `weights.hysteresis` の単位がモデルで異なることが未記載

差動二輪では[score per rad/s]、Ackermannでは[score per 1/m]であり、同じ重み値でも実効的な強さが変わる。
Ackermann側の項は概ね `2 / turn_radius_min`、差動二輪側は `2 * w_max` に比例する。同梱のAckermann設定例
（`turn_radius_min` 1.0、`w_max` 0.8）では偶然ほぼ一致するが、`turn_radius_min` を小さくすると
`weights.hysteresis` が `weights.clearance` を圧倒しうる。

### L5 — Ackermannシナリオ群が差動二輪より薄い

Ackermann 6シナリオに対し差動二輪は17シナリオである。差動二輪側で対応するミューテーションを殺している
`safety_stop`、`corridor_narrow_*`、`corridor_zigzag`、`clutter_field` に相当する世界がAckermann側に無い。
また閉ループ側に操舵の滑らかさを測る指標（差動二輪harnessの `max dw` に相当するもの）が無い。

## 誤りを確認しなかった項目

- 後退時の符号処理。`k = w/v` は符号付き経路曲率であり、`yawRateBound` は `|v|` を使う。fuzz中の
  後退出力3 464件で半径違反0件。
- `applyCommandDeadband` が `v == 0, w != 0` を出力する可能性。`curvature()` が `|v| <= 1e-4` で0を返す
  ため、`velocity_min = 0` でも構造的に不可能。
- `BacCore` の rule-of-three、dangling reference、null参照。copy時にmodelを再構築しており、
  ASan/UBSanで destroy-source-then-use-copy と `vector<BacCore>` 再確保を含めてclean。
- 出力段の `kReachabilityIterations` ループの停止性と `output_admissible` の正しさ。`|out_v|` が
  各反復で狭義単調減少する。
- `limitReachableCommand` の適用順序による旋回半径違反。clampが最後であり、fuzz 72 000 tickで違反0件。
