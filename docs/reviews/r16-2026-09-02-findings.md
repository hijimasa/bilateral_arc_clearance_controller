## 対象と方法

3名のレビューアが独立に担当した。判定はA **Hold**、B **Hold**、C **Conditional Go** である。

**AとBの結論が1点で食い違った**。R15 H4（廊下進入時の接触）についてAは「独立rigの掃引で接触は全セル0」、
Bは「進入オフセット0.396と0.420で接触、侵入127 mm / 211 mm」と報告した。**作成者が第三のrigで検証し、
Bの結果を確認した**。試験fixtureと同一のplant・同一パラメータで進入オフセットを0.002 m刻みに掃引した
結果を以下に示す。Aのrigは掃引が粗く、接触するセルを跨いだものと判断する。

```text
off=0.392 final=(1.543,0.643) contacts=0     traverse 失敗
off=0.396 final=(1.780,0.593) contacts=4419  worst_depth=0.2266
off=0.410 final=(1.723,0.597) contacts=0     traverse 失敗
off=0.416 final=(1.592,0.593) contacts=0     traverse 失敗
off=0.420 final=(1.866,0.592) contacts=8837  worst_depth=0.2317
```

検証手段: plain CMake Release `ctest` 10/10、Debug + ASan/UBSan 10/10、ROS 2 Jazzy / Nav2コンテナ
11/11、production変異計90件超、`main` との状態同期比較（A: 80000行、C: 48000 tick）、乱択閉ループ
12万tick・29万tickの不変条件検査、進入オフセット0.002 m刻み61セル × 2幅、seed掃引7種、
計装ビルドによる分岐到達回数の実測。

## 結論

**統合してはならない。**

R15対応そのものは実体を伴う。`vy = 0` での恒等性は40万点の掃引で`max|diff| = 0`（float完全一致）、
既存2モデルへの回帰は独自分布80000行と48000 tickで0、R15が挙げた変異は申告どおりKILLEDされ、
横移動の安全契約は29万tickで破れ0という独立検証も得られた。修正は過保守化も招いていない
（holonomicの平均指令速度は−3.6%〜−4.2%、廊下掃引では9セルで改善）。

にもかかわらずHoldとする理由は3系統ある。

1. **R15 H4が解消していない**。作成者は進入オフセットを3点でしか測らず「接触は全条件0」と結論した。
   0.002 m刻みで掃引すると接触が再現し、侵入深さはR15時点の6.2 mmから**227 mm**へ悪化している。
   格子点上でだけ成立する修正である。
2. **R15対応が新設したコードが、試験から一度も実行されない**。`stoppable` ラムダ、emergency fallbackの
   ladder、holonomicの減速経路はいずれも到達回数0で、`stoppable` を常にtrueにしても`ctest`は通る。
   作成者は当初この変異のkillを得ていたが、その後property testの加速度上限を1000にして候補段を分離した
   際にkillを失い、再測定しなかった。**R14 M5で作成者自身が指摘した「killを代替なしに失う」の再発**
   である。
3. **R15対応の検証記録が実測と食い違う**。「fallback変異KILLED」「出力段5変異のうち生存1件」
   「safe_speed変異は等価変異」はいずれも再現しない。加えて試験コメント内の記録帯3件と、
   response自身のH4表が実測と異なる。

R11以降、このプロジェクトが繰り返し検出してきたのは「packageが自身について提示するevidenceの欠陥」で
あり、R16はそれが**3ラウンド連続で、同じ作成者の対応文書に**現れたことを記録する。

`test/omni_scenarios.cpp::testNarrowCorridorCentering` のfixtureと同一のplant・パラメータ。上掲の

**`433068a` はオフセット0.400の接触を消したが、0.396と0.420では接触する。** commit messageと

### H2 — 出力deadbandが全admissibility検査の後に走り、publishされるtwistについて不変条件が成立しない

`src/bac_core.cpp::BacCore::process` の `applyCommandDeadband` 適用位置、および
`OmniMotionModel::applyCommandDeadband`。

package自身の契約（`filtered_points`、`remaining_path`、`travel_margin` すべて実装のもの）をdeadbandの
直前と直後で評価した、乱択閉ループ12万tickの結果:

```text
model   deadband前違反   deadband後違反      deadbandが指令を変えたtick
OMNI          0            68 / 109685        36080 / 120000 (30%)
DIFF          0             1 / 111635         2296 (1.9%)
ACK           0             0 / 112408         1292 (1.1%)

POSTVIOL pre(v=0.18772 vy=0.05536 w=-0.00919) out(v=0.18772 vy=0.05536 w=0.00000)
         判定した弧の初接触=1.05094 m / 実際に出す弧=0.4322 m
```

`angvel_min`（既定0.01 rad/s）が判定の**後**で `w` を0にし、crab成分が残るため軌道幾何が変わる。
**deadband前が全モデル0違反であることは `433068a` の修正が内部的に完結している証拠**であり、破れは
publishされるtwistにだけ現れる。機構自体は `main` から存在するが、omniでは30%のtickがdeadbandで
書き換わるため桁違いに顕在化する。

同梱設定・同梱世界では違反0だが、それは余裕が偶然効いているためである。R15がH2に用いた基準——
不変条件の破れを余裕の大きさで正当化しない——をそのまま適用する。

### H3 — 速度governorが完全に前進軸のままで、横移動は同じ壁へ32%速く突っ込む

`src/bac_core.cpp::evaluateProximity` の `const bool forward = current.v >= 0.0f;`、arc refinement、
`side_gap`、および `v_cap` の算出。

正方footprint 0.5 × 0.5、等方margin 0.2、`heading_gain = 0` で、世界と速度を厳密に90°回した2条件:

| 壁までの距離 | 前進時の\|out\| | 横移動時の\|out\| | 差 |
|---|---|---|---|
| 0.60 | 0.2600 | 0.3157 | +0.0556 |
| 0.80–1.00 | 0.2600 | 0.3423 | **+0.0823（+32%）** |
| 1.10–1.30 | 0.2600 | 0.3400 | +0.0800 |
| 1.40以降 | 一致（governor解放）| | |

機構も解析と一致する。前進時は `side_gap < 0 && ahead > 0` の正面衝突枝で `hazard = ahead/lookahead`
により `v_cap = 0.2655` になるが、横移動時は同じ壁が `side_gap = 0.75 >= 0` の側方枝に入り、
`side_ratio = 3.75` でcapが効かない。`side_ratio` は横方向gapの関数であって `vy` の関数ではないため、
**離れる横移動と突っ込む横移動を区別しない**。

R15が根と診断した「`vy` が進行方向を判断する箇所に届いていない」の1階層深い同型であり、`433068a` も
対応資料も触れていない。停止不能にはならない（接触判定は一般化済み）が、予測的減速層が横方向に対して
機能していない。

### H5 — 「safe_speed変異は等価変異になった」は成立しない。符号判断はmodelへ移っただけで、移動先に検査が無い

## main統合についての判断

**統合してはならない。** 統合前に満たすべき条件は次の5件である。

1. **H1** — 進入オフセットを**連続軸として**掃引し直し、接触と恒久停止を除去する。除去できないなら、
   格子点ではなく**区間として**文書化し、commit messageと `docs/algorithm.md`（日英）の
   「0.30から0.40まで完走」を実測に合わせる。現状のまま統合すると `main` の文書が誤りになる。
2. **H2** — deadbandをadmissibility検査の**前**へ移すか、deadband後の指令を再検査する。publishされる
   twistが不変条件を満たさないことは、branchが看板に掲げる性質そのものの反例である。
3. **H3** — 速度governorを進行方向へ一般化する。R15が根と診断した欠陥の1階層深い同型であり、
   R15対応の範囲から漏れている。
4. **H4** — `stoppable`・fallback ladder・holonomic減速経路に到達する回帰を置く。現実的な加速度で回る
   property testか、`test/output_stage_unit.cpp` のholonomic版が要る。
5. **H5** — `withLinearSpeed` の方向復元に前進側のkillを置く。差動二輪の後退側も含めて検査する。

M1〜M13のうち、**M7・M8・M9は文字列の訂正のみで、統合前に済ませるべきである**（実測と食い違う記録が
`main` に入るため）。M10は文書1行とgateの主張の是正で足りる。残るMediumとLow全件は次サイクルで足りる。
