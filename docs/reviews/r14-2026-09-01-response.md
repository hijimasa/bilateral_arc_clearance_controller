# 第14回リリースレビューへの対応

レビューID: `R14`
対象レビュー: [r14-2026-09-01-findings.md](r14-2026-09-01-findings.md)（2026-09-01、`112eb35` 時点。
判定 **Conditional Go**、High 1件・Medium 10件・Low 9件）
対応日: 2026-09-01
対象package: `112eb35` に対する対応。本対応のcommitは `13b3d16`、R14の記録commitは `0586253` である
（規約7に従い、本文と[リリースレビュー履歴](../release_review_history.md)のSHAは対応commit直後の
追記commitで記載した）。
対象benchmark: 該当なし（本対応はbenchmarkを再実行していない）

High 1件とMedium 10件すべてに対応した。Low 9件は次cycleへ送るが、L5・L7・L9は上位項目の修正に含まれる
範囲で部分的に閉じた。

R14が指摘した構造的問題——「修正の効果を測る基準が修正のたびに再導出されていない」——への対応として、
本ラウンドでは**閾値を維持・変更・追加するときは、正常側と破壊側を同一の摂動格子で両側とも掃引し、
その実測帯をコメントに残す**ことを全件で適用した。その結果、閾値を2つ削除し、1つも新設していない。
分離できない量に閾値を置く代わりに、被覆は閾値を必要としない決定論的な単体検査へ移した。

## H1 — 同梱設定ガードがファイルではなくキー集合に紐付いている

**修正**。`readConfigFile` の戻り値を `std::map<key, value>`（最後勝ち・block非認識）から、行番号・
所属block・重複回数を保持する `ConfigFile` へ変更し、`shippedExampleParams` に4層の検査を追加した。
YAMLライブラリは追加せず、依存の無い `key: value` readerのままである。

1. **未消費キーの失敗化**。消費キー24個でも `kAllowedUnconsumedKeys` でもないキーは失敗する。
   allow-listはblock header 3個と `controller_frequency`、`controller_plugins`、`plugin`、`scan_*` 5個、
   `diagnostics_publish_period` の計12エントリで、各行に意図をコメントした。
2. **重複キーの失敗化**。同名キーが2回現れたら失敗する。最後勝ちを廃止した。
3. **block認識**。空値行をsectionとして追跡し、未知sectionは失敗、消費キーは `FollowPath` block内に
   あることを要求する。
4. **数値parseのfail-closed化**。`std::stof` を `std::strtof` + 全消費検査 + `std::isfinite` 検査へ
   置き換えた。

**検証**。R14が「PASSする」と実証した攻撃を実ファイルの複製上で再実行し、すべて `rc=1` になった。

```text

                             suite or listed in kAllowedUnconsumedKeys on purpose
v_samples: 2           FAIL: ... key v_samples (line 62) ...
margin_scale_floor     FAIL: ... key margin_scale_floor (line 62) ...
max_range: 0.5         FAIL: ... key max_range (line 62) ...

```

R14が示した複製block攻撃（`FollowPath` を `weights.hysteresis: 0.6` で壊し、正常な `FollowPathB` を
追記する）も塞がった。

```text

      second block is masking the one users copy
FAIL: the shipped configuration declares weights.hysteresis (line 65) only once; ...

FAIL: the shipped Ackermann example reaches its goal rather than orbiting (closest 0.466099 m,
      travelled 10.526865 m)
```

消費キーをblock外へ移す攻撃も検出する。
`FAIL: the shipped configuration keeps sim_time inside the FollowPath block users copy (found under 'ros__parameters' on line 6)`。

R13 H1が確立した既存のkillはすべて維持している（`weights.hysteresis: 0.6` → orbit FAIL、当該行削除 →
`declares weights.hysteresis` FAIL、`diff_drive` → `selects the Ackermann model (got 'diff_drive')`、

**閉じていない範囲を明示する**。`safety_margin.side: 0.0`、`stop_decel: 3.0`、`footprint.width: 0.3`
は依然として `rc=0` である。これらは**消費キー**であり、H1が指摘した「読まれないキー」ではなく、
閉ループのアサーションがこれらの値に感度を持たないという別の問題（R14 L8）である。特に

## M1 — 差動二輪出力段の挙動変化が固定されていない

**修正**。`test/output_stage_unit.cpp` を新設した（ctest名 `BacOutputStageUnit`、label
`regression;diff_drive`）。証人はすべて `BacCore::process` を1 tick直接呼ぶ決定論的入力であり、
`main` との状態同期sweepから探索して点を1〜2個まで削ったものである。

| 検査 | 固定する性質 |
|---|---|
| `decel-a` / `decel-b` | 減速しても並進を維持し、**曲率を保存**する |
| iteration depth | reachability補正が1回でなく複数回反復する |
| rotation guard (a) | 旋回不可なら厳密に `(0,0)` かつ `STOP` |
| rotation guard (b) | 旋回可能なら `braking.w` を保持し `STOP` にしない |

黄金値は避けた。曲率検査は実行時に導出した値と比較する。`limits.acc_w = 0` の対照runで
reachability制限だけを無効化し（`sampleCandidates` とスコアリングは `acc_w` を読まないため候補勝者は
同一）、その未制約勝者を取得して、公開APIの `limitReachableCommand` でclamp値を得たうえで
`out_w / out_v == clamped_w / best_v` を検査する。実測は勝者 `(0.120000, 0.479167)` → clamp
`(0.120000, 0.300000)` → 出力 `(0.093790, 0.234475)` で、曲率2.500000 1/mが一致する。旋回ガード側は
`result.min_proximity_norm = 1.2458 > 1.0` を併せてアサートし、`(0,0)` が緊急停止層ではなく出力段に
由来することを示している。

**検証（ミューテーション）**。

```text
c01 曲率保存減速をmain相当へ戻す
  FAIL: decel-a: the reachability stage keeps translating instead of braking to zero (v = 0.000000)
  FAIL: decel-b: deceleration preserves the curvature of the contact-checked arc
        (3.492260 vs 2.515833 1/m)
c02 fallbackのrotation_admissibleガード削除
  FAIL: an unreachable output with no admissible rotation emits exactly zero (0.000000, -0.245000)
  FAIL: that tick reports STOP rather than AVOIDING
c03 kReachabilityIterations 8 -> 1
  FAIL: repeated reachability correction finds a translating command in the corridor (v = 0.000000)
c02b fallbackが常に out_w = 0（c02の逆向き）
  FAIL: an admissible rotation keeps the reachable braking yaw rate (0.000000 vs -0.245000)
```

`8 -> 2` と `8 -> 4` も同様にKILLEDである。

**生き残るものを正直に記録する**。`8 -> 5` と `8 -> 7` はSURVIVEする。上限値8そのものは固定して
いない。20万tickのsweepで5回目の反復を要するtickは32件、8と7を区別するtickは**1件のみ**であった。
この1件を証人にすればc03を全深度で殺せるが、正常帯と破壊帯の間に余裕がゼロのtripwireになる。
R14 M3・M4が批判した閾値の立て方を再発させないため採用せず、余裕3反復ぶんを残す「5回以上」の固定に
留め、その旨と実測値をテスト内コメントに明記した。

**CHANGELOG.rst**。既存のin-place rotationの項（R11 L1由来）が本件の一部を既に記述していたため、
重複させず既存2項を書き直した。出力段の変更内容、観測された差分がすべて保守側であること、実測率
（同梱 `diff_drive` 設定で20万tick中1014 tick、0.5070%）、閉ループ10世界中9世界がbit-identicalで
残り1世界が最大2 mm、`avoid_status` 購読者が従来 `AVOIDING` だったtickに `STOP` を見うることを記載
した。

**独立確認**。指摘の測定値を鵜呑みにせず、`main`（`f8b1d04`）の `bac_core.cpp` を別途ビルドし、
より過酷な入力分布（散乱・通路・開口壁・近接障害の4種混在）で状態同期20万tick比較を行った。差分は
3291件（1.6455%）でクラス構成は指摘と同一（A 2408 / E 312 / C 291 / G 208 / H 72）、そして
**新実装の `|v|` が旧より大きいtickは0件、`|w|` が大きいtickも0件**、**status変化は
`AVOIDING` → `STOP` が2699件、逆方向は0件**であった。「すべて保守側」と「`avoid_status` が `STOP` を
見うる」の両方が独立に裏付けられた。

## M10 — 履歴メタデータの陳腐化（3回目の再発）

**構造的に修正**。R12 L4・R13 L5・R14 M10はいずれも「修正commitが自分自身のSHAを書けない」ことに
起因する同一欠陥である。`docs/reviews/README.md` と `README.en.md` の更新規則に**規約7**を追加した。

> 履歴の`現在の状態`が記載する対象package commitは、responseのcommit自身では書けない（commitは自分の
> SHAを含められない）。**response commitの直後に、そのSHAを記載する追記commitを必ず作る。**

本ラウンドはこの規約に従い、response commitの直後に履歴のSHA行を更新する追記commitを作る。あわせて
索引の「全10回」という数値表記を非数値へ変更し、回数の陳腐化そのものが再発しないようにした
（L9の一部）。
