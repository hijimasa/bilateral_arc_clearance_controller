## 対象と方法

B: 検証装置と、作者がcommit message・コメント・文書に記載した**実測値そのものの独立再現**。
C: Nav2結合・公開API互換性・設定・パッケージング・日英文書・コンテナ検証。

検証手段: plain CMake Release `ctest` 10/10、Debug + ASan/UBSan（`detect_leaks=1`）10/10、

## 結論

**統合してはならない。** ただし理由は幾何でも既存利用者への影響でもない。

幾何の中核は主張どおり健全である。回転中心を `(-vy/w, v/w)` へ移す一般化は独立導出と代数的一致で
確認され、旋回枝の接触解は全クラブ角・両符号 `w`・後退で厳密（総当たり41.6万サンプルとの最大差
3e-4 m = 離散化幅）、楽観側（接触見逃し）は0件である。既存の差動二輪・Ackermann利用者への影響も
無い（harnessとAckermannのmd5一致に加え、独自分布4800行・4万tickで完全一致、`cmd_vel.linear.y` は
厳密に0、`goal_heading` は出力を変えない）。公開APIはsource互換である。

問題は一点に集約される。**`vy` は候補生成と幾何評価には行き渡ったが、「進行方向」を判断する4か所には
行き渡っていない。** その結果、本branchが看板に掲げる「採点し接触判定した軌道が走る軌道である」と、
本packageの中心的保証である「接触前に停止できない候補は採用しない」が、純横移動指令について成立
しない。実衝突は限定的（1573 world × 200 tickでは接触0、ただしH4は接触を再現した）だが、これは
出荷設定の余裕が偶然効いているためであり、不変条件の破れを余裕の大きさで正当化することはできない。
R14が確立した基準——「測定された正常帯と破綻帯」で語れるのは閾値であって不変条件ではない——に照らし、
判定を **Hold** とする。

あわせて、作者が記載した実測値のうち**6件が再現しなかった**。R14が「packageが自身について提示する
evidenceの欠陥」を繰り返し問題にしてきた分類が、そのR14の対応を書いた同じ作者の手で再発している。

## High

### H1 — `v = 0` 行の候補が接触判定にもDWA制動判定にも到達しない

`src/bac_core.cpp:940` の `evaluate_candidate` 内 `if (std::fabs(v) <= 1e-3f)`。この分岐は
`command.v` だけを見て `command.vy` を無視し、候補を「その場旋回してから前進する」turn-then-go軌道
として採点する。`OmniMotionModel::sampleCandidates` は `forward_speeds.push_back(0.0f)` で必ず
この行を作るため、**純横移動候補の一族全体（実測96候補中16〜32個）が
`evaluateArcWindows(command)` にもDWA制動判定にも到達しない**。

計装ビルドで `ROTBRANCH count: 128 / ARCBRANCH count: 0`。乱択8000 trialで、出力された指令自身を
事後に接触判定し直すと制動条件を破る例が12件見つかった。

```text
trial 1155 tick 0: OUT v=0.00000 vy=-0.25408 w=0.62147 speed=0.2541 | blocking_s=0.2154 v_safe=0.0963 status=AVOIDING
trial 1292 tick 0: OUT v=0.00000 vy= 0.23346 w=0.40130 speed=0.2335 | blocking_s=0.2149 v_safe=0.0938 status=AVOIDING
```

指令速度が停止可能速度の約2.5倍である。主張「スコアされ接触判定された軌道が走行される軌道」の直接
的な反証であり、`docs/algorithm.md` が無条件に述べる判定規則の反証でもある。

### H2 — 候補段の制動距離が前進成分だけで計算され、純横候補は制動距離ゼロで許容される

`src/bac_core.cpp:995-1022`。出力段は本branchで3自由度へ一般化された（`travel_margin`、`speed()`）
が、**候補段の同じ計算は `v` のままである**。`needed = v*v/(2*stop_decel) + |v|*brake_reaction_time`
（1016行）、`margin = (v >= 0) ? front : rear`（1014行）、`dist_block = |v| * sim_time`（995行）。

```text
pure crab left, point 0.60 abeam  blocking_s=0.3500 free_run=0.1500 needed(v only)=0.0000 -> admitted
forward,        point 0.60 ahead  blocking_s=0.2500 free_run=0.0500 needed(v only)=0.0863 -> REJECTED
```

閉ループでも再現する。同一世界で `v_max = vy_max = 0.6` として壁へ前進した場合の最接近は0.2900 m、
真横へ移動した場合は **0.1655 m** で、`safety_margin.side` 0.20を侵す。同梱設定（0.4 / 0.3）では
0.51 / 0.48で安全だが、それは偶然である。閾値は速度0.491 m/sであり、`vy_max`・`safety_margin.side`・
`stop_decel` の関係をvalidatorも文書も拘束していない。しかも `docs/nav2_integration.md` は
「`limits.vy_max` は観測できている範囲から決める」と値を上げる方向へ誘導している。

H1とH2は独立した欠陥である。H1は候補が判定に到達しないこと、H2は到達した候補の判定式が前進成分
だけを見ることである。

### H3 — emergency / escape層が横速度を一切見ない

`src/bac_core.cpp:435`、`:899`、`:1205`、および `evaluateProximity`（本branchで無変更）。3つの穴が
連鎖する。

1. **制動優先判定に `vy` が無い**。`if (fabs(current.v) > 0.05f || fabs(current.w) > 0.1f)` のため、
   計装ビルドで `ESCAPE_ONLY entered: current(v=0.0000 vy=0.3000 w=0.0000) speed=0.3000` となる。
   **`vy_max` 一杯で横移動中の車体が「停止中」と分類され、硬いemergency制動を飛ばす。**
2. **escapeゲートがx軸だけ**。`const bool towards = v * proximity.emergency_x > 1e-6f;` は `v = 0`
   の候補で常に `false` になり、障害点が真横でもそちらへ向かう横移動が許可される。
   `proximity.emergency_y` はどこからも参照されない。
3. **fallbackの横速度が無ゲート**。`out_v = 0.0f; out_vy = braking.vy;` により、実測で
   `current(v=0.00 vy=0.30) -> status=STOP out(v=0.0000 vy=0.2600 w=0.0000)` となる。壁は `y = +0.33`
   にあり、出力 `vy = +0.26` は**その壁へ向かっている**。`out_v` は加速度制限なしに0へ落とすのに
   `out_vy` だけランプで残す非対称も一貫していない。

緊急ゾーンの速度依存延長も `+x` 方向のみである。`v = 0.10, vy = 0.30` で
`zone_extension_used = 0.0163` に対し、進行方向の実制動距離は `0.0941` である。0.32 m真横の点で
`prox = 0.5833`（emergency成立）にもかかわらず `vy = 0.26 m/s` を出し、statusはSTOPを報告する。
**同じ幾何を90°回すと厳密に停止する。**

「前進専用の車体で安全だったものが横方向で到達可能になったか」への答えは **yes** である。

### H4 — 廊下進入時に車体が壁へ接触し、以後復帰しない

`test/omni_scenarios.cpp::testNarrowCorridorCentering` は進入オフセット0.30 mの1点しか走らせて
いない。オフセットを振ると破綻する。

```text
幅1.1 m offset 0.32/0.34/0.36/0.38/0.40/0.45 -> OMNI final x 1.55前後で恒久停止 / DIFF は全て走破
幅1.2 m offset 0.40 -> OMNI final x 1.7302, collided=1, min range 0.3449
        CONTACT tick=197 t=9.85 pose=(1.7302,0.5982,-0.0735) pt_body=(0.3438,0.0271) depth_front=0.0062
```

壁点がfootprint（`front` 0.35）に6.2 mm侵入し、以後2400 tick中2214 tickが停止指令のままで復帰
しない。`safety_margin.front = 0.2 m` の契約に対し0.206 mの不足である。

`0f0a5fb` のcommit messageと `docs/algorithm.md`（日英）が述べる「1.0 m以外は参照が通る全ての通路を
完走する」は、**進入オフセットを0.30 mに固定した場合にのみ真**である。統合すると `main` の文書が
誤った状態になる。

### M4 — 出力段の「速度ベクトルで判定する」不変条件を前進軸へ戻す変異5件がすべて生存する

| ID | 内容 | 安全上の帰結 |
|---|---|---|
| T5 | 停止判定 `out_command().speed()` → `fabs(out_v)` | stop-before-hitの比較対象が前進成分のみになり、斜行指令は真の速度が `v_safe` を超えても許容される |
| T4 | 接触判定horizonを `fabs(out_v) * sim_time` へ | 斜行分だけ接触判定の見る距離が短くなる |

### M8 — 直進枝のcrab幾何は厳密ではなく保守側の近似である

総当たり掃引矩形との照合（crab角12種 × `w` 9種 × 各3000点 = 41.6万サンプル）:

- **旋回枝は全crab角・両符号 `w`・後退で厳密**（最大差3e-4 m = 総当たりの離散化幅）。
- **直進枝は軸非平行の進行方向で最大0.67 m早すぎる側にずれる**（0.7 × 0.5 m車体、`ang = +0.200` で
  worst 0.6400）。`ang = 0, ±π/2, π` では3e-4まで厳密。
- **楽観側（接触見逃し）は41.6万サンプル中0件** — 安全側の近似である。

原因は直進枝が掃引領域を `(u, n)` 系の軸平行bounding boxとしてモデル化していることである（実際は
六角形）。安全側だが、「支持関数化により厳密」というcommitの枠組みとは食い違い、crab時に過剰制動を
招く。H4（狭路に入れない）の一因である可能性がある。

### M9 — centering bias加算後に `wrapAngle` が無い

`src/bac_core.cpp:789`。直後のgoal-headingブロックは `wrapAngle` するがこの行はしない。
`|relative_path_heading| > π - 0.6 * tightness ≈ 2.54 rad` で ±π を越え、P制御の誤差が「短い方」で
なくなる。

```text
tangent +3.10 bias +1.0 : as-coded pose_ref +3.7000 -> yaw +1.0000
                          wrapped  pose_ref -2.5832 -> yaw -1.0000
```

収束はするが、2.58 radで済むところを3.70 rad回る。差1.12 rad（64°）の余分な車体回転を**まさに狭い
通路の中で**行う。このバイアスが「crabより車体回転の方が掃引が狭い」という理由で導入されたことを
考えると逆行している。

## main統合についての判断

**統合してはならない。** High 4件はいずれも安全に関わる不変条件の破れであり、`vy` が「進行方向」を
判断する4か所に行き渡っていないという単一の根に由来する。

- `evaluate_candidate` の `v = 0` 分岐（H1）
- 候補段の制動距離計算（H2）
- emergencyの制動優先判定とescapeの `towards` ゲート（H3）
- `safe_speed` の符号（下記）

**H2の派生として記録する符号誤り**: `src/bac_core.cpp:1183` の
`safe_speed = (out_v > 0.0f ? 1.0f : -1.0f) * v_safe` は `(v, w)` だけの世界では `out_v` の符号が
進行方向と一致していたため正しかったが、`out_v <= 0 かつ vy != 0`（`v = 0` 行の勝者）では
`safe_speed` が負になり、`OmniMotionModel::withLinearSpeed` がtwist全体を負でスケールして**横移動も
yawも反転する**。

```text
SLOW in(v=0.00000 vy=-0.16868 w=-0.52604) safe=-0.10237 -> out(vy=+0.10237 w=+0.31926)  *** REVERSED
SLOW events: 875   REVERSED: 13
単体でも再現: dot(in_xy, out_xy) = -0.017306
```

差動二輪は健全である（曲率保存により後退時も正しい）。

実衝突の再現はH4の1件（廊下進入時の6.2 mm侵入）に留まり、1573 world × 200 tickのロールアウトでは
両モデルとも接触0である。しかしこれは出荷設定の余裕が効いているためであって、H1–H3は「測定された
正常帯と破綻帯」で語れる閾値ではなく**不変条件そのものの不成立**である。R14が確立した基準に照らし、
余裕の大きさで正当化することはできない。

統合前に満たすべき条件:

1. **H1・H2・H3と `safe_speed` の符号** — 「進行方向」を判断する4か所を `speed()` と
   `travel_margin`、および `(v, vy)` ベクトルへ一般化する。出力段では既に行われているため、同じ
   一般化を候補段とemergency層へ適用する作業である。
2. **H4** — 廊下進入時の接触と恒久停止を修正するか、進入オフセットの制約として文書化する。現状の
   commit messageと `docs/algorithm.md`（日英）は逆のことを主張している。
3. **M12・M13・M14** — 実測と食い違う記載と、本数の誤り、`main` に無いoverclaimを訂正する。統合
   すると `main` の文書が誤った状態になる。
4. **M1** — governorのcapが `limits.v_min` で緩む件。ライブラリ既定値 `-0.1` で主張が偽になる。

M2–M11、M15、Low全件は次サイクルで足りる。ただしM2とM3は、**R14が確立し、R14対応が「全件で適用
した」と宣言した「両側を同一格子で掃引する」基準が、その直後のラウンドで再び満たされていない**
事例である。次ラウンドでの同型再発を避けるため、掃引した格子の定義そのもの（何を何点振ったか）を
テスト内に記録することを推奨する。
