# リリースレビュー記録規則

このディレクトリは、リリース判断に至るまでの指摘と対応を、後から検証できる形で保存する監査用
アーカイブである。利用者向けの現行仕様は上位ディレクトリの文書を正とし、過去レビュー中の記述を
現在の仕様として引用しない。

## ファイル名

```text
rNN-YYYY-MM-DD-findings.md
rNN-YYYY-MM-DD-response.md
```

- `rNN`: 2桁の連番による不変のレビューID。公開後は再採番しない。
- `YYYY-MM-DD`: findingsを確定した日付。ISO 8601形式を使う。
- `findings`: レビュー時点の指摘、根拠、判定。
- `response`: 指摘に対する修正、検証結果、残項目。

日付だけでは同日中の複数レビューを区別できないため、必ずレビューIDを併記する。commit SHAは
response作成中に変わり得るためファイル名には含めず、文書冒頭のメタデータへ記録する。`#1`のような
文字列はURL fragmentやshellで特別扱いされるため、ファイル名には使わない。

## 文書冒頭の必須情報

R11以降のfindingsとresponseには、該当する範囲で次を記録する。

- レビューID
- レビュー日
- 対象package commit
- 対象benchmark commit
- 対応するfindingsまたはresponseへの相対リンク
- 判定（`Hold`、`Conditional Go`、`Go`）

必要なら`geometry`、`adapter`、`benchmark`、`provenance`、`documentation`などの検索タグを本文へ
追加してよい。タグは補助情報であり、レビューIDの代わりには使わない。

R01〜R10は当時の本文を監査証跡として維持し、移行時にはレビューID、ファイル名、相互リンクだけを
正規化した。対象commitや判定が独立したメタデータ行ではなく、冒頭または結論節に記録されている文書も
ある。

## 更新規則

1. findingsとresponseは別ファイルとし、同じレビューIDと日付を使う。
2. 両文書を相互リンクし、[レビュー履歴](../release_review_history.md)にも1行追加する。
3. 後続レビューで結論が変わっても、過去文書を現在形へ書き換えない。後続文書で撤回・訂正を明示する。
4. 誤字やリンク切れを直す場合は意味を変えない。根拠や判定を変える修正は新しいレビューとして記録する。
5. sourceへの参照は、可能ならsymbol名または見出しanchorを使う。可変な`#L123`形式を根拠の唯一の
   識別子にせず、必要に応じて対象commitも併記する。
6. 移動・改名後はREADMEを含む全Markdownの相対リンクを検査する。

## 現在の記録

全10回の要約、最終判定、撤回事項は[リリースレビュー履歴](../release_review_history.md)を参照する。
個別文書は当時の判断を保存しているため、履歴文書と矛盾する場合は後のレビューを優先する。
