### H1 — 独立接触検査をゲートの上へ出した。ただしH1は「閉じた」のではなく一段上へ移った（部分的に閉じた）

`test/omni_scenarios.cpp` の第1掃引・第2掃引で、`independentContactDistance` の呼び出しが
`eval.blocking_s >= 1e9` と `free_run <= 0` の**下流**にあった。評価器が接触を見落とすと、そのtickは
検査対象から外れるだけで違反にならない。第1掃引では移動8314 tickのうち **8197 tick（98.6%）**が
そこで落ちていた（1巡目の実測。2巡目では測り直していないが、R19の検証担当2名が独立に再測定して
一致している）。

独立検査をゲートの**上**へ出し、`independentSearchWindow` を新設して評価器と同じ窓で打ち切った。
窓は評価器の `evaluate` と `makeSweptFrame` から組み直したもので、

- `s_max = horizon + lead`。`lead` は進行方向への支持幅
  `(dx>=0 ? front*dx : rear*dx) + width/2 * |dy|`。掃引は
  `evaluateArcWindows(points, out, horizon, horizon)` を呼ぶので
  `s_max = max(blocking, clearance) + lead` が `horizon + lead` になる。
- 旋回指令ではさらに `s_angle_cap = turn_radius * eval_angle_max`（`turn_radius = speed / |w|`）で
  抑える。評価器は接触ソルバへ `min(s_max, s_angle_cap)` を渡している。

**窓の打ち切りは必須である。** ゲートを外すだけだと無変異でも第1掃引 **7件**・第2掃引 **53件**の
偽陽性が出る（1巡目の実測。2巡目・3巡目では測り直していないが、R19の検証担当が独立に再測定して
一致している。`eval_angle_max` = 1.05 rad を超えた先の接触まで停止を要求してしまうため）。

## 次サイクルの筆頭 — 独立検査が「接触距離0」のクラスを検査対象外にしている

**本ラウンドでは実装していない。次サイクルの筆頭項目として記録する。**

H1の対応で独立検査はゲートの上へ出たが、残っているゲート `own_free_run > 0.0f` が
**「接触距離0」のクラスを丸ごと検査対象から外している**。`independentContactDistance` が0を返す
（点が最初から車体矩形の内側にある）と `own_free_run = -margin < 0` になり、そのtickは検査されない。
そのため `geo_fca_inside_removed`（`firstContactArcLength` の「点が最初から車体内部なら0を返す」
早期returnを削る変異）は、**実際に評価器が真の接触を見落とすのに不可視**である。

自分で試作して測った（scratch copyのみ。作業ツリーには入れていない）。移動tickごとに、独立ソルバの
接触距離が共有窓の内側に入るときだけ、評価器の `eval.blocking_s` がそれより遠いかを数える
assertion（MISSカウンタ）を、`own_free_run > 0` ゲートの**上**に置いた場合:

| 条件 | 第1掃引 | 第2掃引 | 既存assertionの独立違反 |
| --- | --- | --- | --- |
| 無変異 | 窓内117 / **MISS 0** | 窓内3150 / **MISS 0** | 0 / 0 |
| `geo_fca_inside_removed` | 窓内119 / **MISS 2**（真の接触 0.000000 m に対し `blocking_s` = 0.233117） | 窓内3150 / MISS 0 | **0 / 0** |
| `rho_max` ×0.95 | 窓内131 / **MISS 41** | 窓内3165 / **MISS 146** | 1 / 11 |

つまり (a) 無変異では0件で空虚でなく、被覆も現行と同じ117 / 3150（コスト0）、(b) 現行の全assertionが
見逃す `geo_fca_inside_removed` をKILLし、(c) `rho_max` 系の検出力を 1 / 11 から 41 / 146 へ上げる。
**次サイクルではこれを本体へ入れることを提案する。** 本ラウンドで入れなかったのは、掃引の
assertion を増やす変更は独立に検証されるべきで、本ラウンドの範囲（R19指摘への対応と、その1巡目が
持ち込んだ欠陥の除去）を超えるからである。

次サイクルの担当に向けて、**そのまま入れればよいものではない**点を2つ記録する（R19検証）。
第一に、このカウンタが検出するものは一様ではない。**`geo_fca_inside_removed` を可視化する増分2件は
退避領域（escape regime）のtickである**——独立接触距離が margin 以下になり、掃引が明示的に除外して
いる領域で、製品はここに `evaluateProximity` の emergency 層を持つ。したがってその2件について
欠けているのは公開twistの安全不変条件ではなく**評価器の健全性**の検出である。一方 `rho_max`×0.95 の
MISSは大半が退避領域の**外**であり（実測: 第1掃引41件中28件、第2掃引146件中143件が
`own_free_run > 0`）、こちらは既存assertionと同じ領域での検出力向上である。R19検証: ここには
「このカウンタが拾うのは退避領域である」と一般化して書いていたが、特殊例を全体の性質として
述べたものだった。
第二に、無変異での偽陽性0はこの2掃引でしか測っていない。`ignore_box` や `max_range` で除かれた点、
および他の構成での偽陽性の不在は**未測定**である。

なお H1 の共有定数 `eval_angle_max` の盲点は、このMISSカウンタでも解消しない（窓が同じだから）。
そちらは別の項目として残る。
